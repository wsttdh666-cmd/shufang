# 番茄下载引擎：两块核心算法研究

研究对象：`zhongbai2333/Tomato-Novel-Downloader`（书房内置的那个 Rust 引擎）的闭源部分。
方法：① 读它从 `Dlmily/Tomato-Novel-Downloader-Lite` fork 时留下的公开 Python/Java 源；
② 对 Rust 二进制做字符串 + 模块结构分析（反汇编到字符串合并层停手）；③ 公开逆向资料互证。

结论先行：**签名这块基本看懂了，能复现；正文解密的流程看懂了，AES 的"模式/IV"靠证据推断、没到逐字节确认。**

---

## 一、正文解密（register_key → batch_full → 干净文字）

### 整条流水线
1. 目录接口拿到每章的 `item_id`。
2. `POST /reading/reader/batch_full/v?...`（带设备参数和签名头）批量取正文。返回里每章有
   一段**加密正文** + 一个 **`key_version`**（二进制里字符串：`batch_full key_version(first)=`）。
3. 按 `key_version` 调 `POST /reading/crypt/registerkey` 换该版本的 **AES 密钥**，本地缓存
   （字符串：`local_register_key_version=`、`fetch_register_key_once begin`）。同一版本不用重复换。
4. 正文：**base64 解码 → AES 解密 → deflate 解压 → UTF-8 文本**。
5. 解压出来是带 `<p idx="N">…</p>` 标签的 HTML（这一步有**铁证**，见下）。

### 证据链
- **用到的 crypto crate**：二进制里只链了 `aes-0.8.4` + `cipher-0.4.4`（RustCrypto 裸块加密 + trait），
  **没看到独立的 `cbc`/`ctr`/`ecb` mode crate 字符串**。
- **压缩**：大量 `flate2` / `miniz_oxide` / `fdeflate` / `inflate 1.3.1` → 正文确实是压缩过的（deflate/zlib）。
- **密钥处理**：`Invalid key length:`、`md5hex must provide at least 32 bytes`、`GenericArray`
  → 密钥可能由 md5 的 hex（32 字符 = 16 字节）得来，AES-128。
- **铁证**：Lite 版的 `2.py` 处理"官方 API"返回的正文时用的是
  `re.findall(r'<p idx="\d+">(.*?)</p>')`。也就是说**解密+解压之后就是 `<p idx=>` 的 HTML**——
  这反向确认了流水线最后一步的产物形态。
- 公开资料里字节系接口普遍是"AES 解密再 inflate"的套路（如社区 gist 里的 `CryptoJS.AES.decrypt` + `pako.inflate`）。

### 还不确定的
- **AES 的模式**：没有 cbc/ctr crate 字符串，倾向 **AES-128-CBC**（所有公开的番茄/fqnovel 解密实现都是 CBC，
  且 CBC 可以不依赖 mode crate、手写异或前块实现）——但也可能是 ECB 或手写 CTR。**没到反汇编逐字节确认**。
- **IV 怎么来**：CBC 的 IV 常见是固定值、全 0、或取密钥前 16 字节，这个没确认。
- **registerkey 返回的密钥本身是否再套一层**（RSA/SM4 包一层再给）没确认——`register_key.rs` 里确实
  有签名动作，但密钥解包细节在内联代码里，被 Rust 的字符串合并挡住了。

> 卡点说明：Rust release 把所有字符串字面量拼成一个大 blob，代码用「blob 基址 + 偏移」引用，
> 直接按字符串地址做 xref 匹配不到。要继续就得先定位 blob 基址、再按偏移+长度还原每个 `&str`，
> 是另一个量级的活，而且番茄一更新就可能变。

## 二、请求签名（四个头）

番茄 App 的接口要四个头：`X-Khronos`、`X-Gorgon`、`X-Ladon`、`X-Argus`。没有有效签名接口直接拒。

### X-Khronos —— 完全看懂
就是 **Unix 时间戳（十进制字符串）**。其它三个头都以它为输入。

### X-Gorgon —— 完全看懂，可复现
Lite 的 `fanqie_signer.py` / `foursign_pure.py` 有可读 Python 实现，作者称真机抓包验证过。算法：
1. 拼一个 **20 字节数组**：
   - `[0:4]` = `md5(URL查询参数)` 的前 4 字节
   - `[4:8]` = `x-ss-stub` 的前 4 字节（`x-ss-stub` = 请求体的 md5；无请求体用 `md5("undefined")`）
   - `[8:12]` = `md5(Cookie)` 的前 4 字节（无 Cookie 填 0）
   - `[12:16]` = 0
   - `[16:20]` = 时间戳 hex 的前 4 字节
2. 过一个 **RC4 式置换表**（`_encryption_table`，用常量 `HEX_DIGITS=[30,64,224,217,147,69,0,180]` 生成 256 字节表），
   再 `_initialize`（逐字节查表 + 异或）。
3. 过 `_handle`：对每字节做「半字节翻转 ⊕ 下一字节 ⊕ 位反转(RBIT) ⊕ 20，再按位取反」。
4. 输出 = 前缀 **`8404`**（真机抓包确认；Java harness 里写的 `0404` 是旧的、错的）
   + 常量字节 `HEX_DIGITS[7,3,1,6]` + 第 3 步的 20 字节 hex。

### X-Argus / X-Ladon —— **两份开源实现打架，这是最大疑点**
- **Lite 作者（Python）**：称拿**三组独立真机抓包逐字节验证过**，这俩对番茄 reading 接口就是**短签**：
  - `x-argus = base64(小端 4 字节时间戳)`
  - `x-ladon = base64(大端 4 字节时间戳)`
  - 并明确说"从 tiktok-signer 照搬的 protobuf+Simon 长签整个是错的算法"。
- **zhongbai 的 Rust 版（书房在用的）**：模块里有完整的 `signing/argus.rs`、`signing/ladon.rs`、
  `signing/sm3.rs`——**用 SM3（国密哈希）实现了完整签名**，二进制字符串也写着
  `registerkey: X-Argus generated by pure Rust`。这**不是**时间戳短签。

**我的判断**：两者很可能针对**不同 App 版本 / 不同接口**。合理的解释是——纯读正文的接口宽松，
收短签就行（Lite 验证到的）；而 `crypt/registerkey` 这种涉及密钥下发的接口要**完整的 SM3-Argus**
（zhongbai 专门实现了）。没有真机抓包，我没法判定哪个对当前线上版本成立。这是需要抓包才能收口的点。

### 另一条线：APK 里的 ISEC/SM4
番茄 APK 反编译里有 `cn.com.infosec.mobile.isec`——**Infosec 的国密 SDK，带 SM4（CBC/ECB）**。
这更像是**设备注册 / 签名那一层**用的（和 SM3-Argus 呼应），正文解密是另一套（AES+inflate）。两者别混。

## 三、对书房的实际意义

- 书房现在是把 zhongbai 的 arm64 二进制当黑盒跑。上面这些**没有一条需要落进书房代码**——
  书房不自己签名、不自己解密，全交给那个引擎。所以这份研究是"知其所以然"，不改现有功能。
- **为什么番茄一更新引擎就可能失效**：签名（尤其 SM3-Argus）和 key_version→密钥这套是番茄的风控，
  番茄改参数/改密钥派生，旧二进制就签不出合法请求或解不出正文。修复只能等原作者出新版二进制。
- 要**自己摆脱对那个二进制的依赖**（纯 JS/Kotlin 复现），签名这块 X-Gorgon 能照 Python 抄，
  但 X-Argus 到底要短签还是 SM3 完整签得先抓包定夺，正文 AES 的模式/IV 也得抓一组真实密文+已知明文来标定。
  工作量不小，且随番茄更新过期——不建议，除非番茄把二进制这条彻底封了。
